## Readiness failure and attribution

Exact failure:

> fireside definitive readiness failure after 3 identical samples: frontend login returned 404

The pre-launch environment captured
`https://phase5-fireside.templates.twodart.localhost`. The
[actual launcher log](phase-5-metrics/two-tier-smoke-v3-20260903T1229+0800-b47a35d-r21/fireside-templates-after-failure.log)
registered `https://templates.twodart.localhost` on port 4640 and reported Next
ready in 459 ms. The [shared routes snapshot after failure](phase-5-metrics/two-tier-smoke-v3-20260903T1229+0800-b47a35d-r21/routes-after-failure.json)
retains that canonical registration and no prefixed frontend entry. No successful
raw frontend fetch was captured during this attempt.

Read-only Git inspection found the Fireside linked worktree detached at the exact
approved revision. The pinned `portless-prefix.sh` deliberately returns no prefix
for detached HEAD; `dev-mprocs.sh` regenerates the URLs from live Git state on
startup. The harness had captured a stale, previously prefixed URL. This is a
checkout/launcher namespace mismatch, not evidence of a Firestore failure or a
reason to alter login routing.

The harness performed shutdown automatically; subsequent checks found no gate
tmux session, owned stack processes, or current-boot OOM/resource evidence. The
next correction restores a named linked-worktree branch without changing its
commit and checks URL/prefix agreement before startup. The fixture is frozen
before that correction. No browser-runner, workload, or manifest changes follow
from this failure.
