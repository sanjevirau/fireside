## Attribution

The Fireside Images Portless wrapper reported `-- Using port 4448`, launched
with `PORT=4448`, and logged a successful listener on `127.0.0.1:4448`.
TwodartNet's independently launched wrapper also reported `-- Using port 4448`.
Kestrel then failed verbatim with
`System.IO.IOException: Failed to bind to address http://127.0.0.1:4448: address already in use.`
and `dotnet watch` waited for a file change. Application readiness consequently
expired after 1,200 seconds with only `marker:dotnet.log` and
`probe:twodartnet-health` unmet. The exact relevant ANSI-stripped lines are in
[`supplemental/portless-collision-excerpt.txt`](phase-5-metrics/two-tier-smoke-v3-20260904-27e96b6-r35/supplemental/portless-collision-excerpt.txt).

Portless 0.11.1's readable source explains the race: each `run` invocation
calls `findFreePort()` before acquiring the route-store lock. The probe socket
is closed as soon as a port is found, so concurrent wrappers can both observe
the same port as free before either child binds it. The later route-file lock
serializes JSON updates but does not reserve the application port. Portless
already exposes `--app-port` for a fixed application port.

This is a harness/infrastructure failure, not a Fireside product result and not
a Twodart application defect. Fireside browser journeys and soak never began;
the conditional full-data gate did not launch. Cleanup left no active gate
process or listener, and the host retained zero failed units and zero
current-boot OOM/resource evidence.

## Required correction

The Phase 5 harness must assign unique fixed Portless application ports to all
autostart application processes in both isolated stacks, include those ports in
the existing quiescent-listener preflight, and stage `--app-port` into each
stack's mprocs configuration before launch. Hostnames, Twodart revision,
manifest, protected browser runner, workload, duration, and thresholds remain
unchanged.
