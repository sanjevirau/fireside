## Exact failure and attribution

The [Fireside browser diagnostic ledger](phase-5-metrics/two-tier-smoke-v3-20260903T1613+0800-2dc275c-r23/browser-fireside-initial.json.diagnostics.jsonl)
records the required cache GET returning 200 at `08:15:44.990Z`, followed three
milliseconds later by `Failed to fetch local cache data: SyntaxError: Unexpected
token '\u001f' ... is not valid JSON`. The complete error text, response URL/status,
and loader DOM text are preserved verbatim in that ledger. The cache WebSocket
opened and received its welcome frame and a later ping. Document and router
both stayed on `/login/overview`.

The unchanged runner then timed out after 180,000 ms waiting for `#workEmail` to
be visible. That is the downstream symptom of the loader error, not evidence
of a routing defect. See the [exact runner error](phase-5-metrics/two-tier-smoke-v3-20260903T1613+0800-2dc275c-r23/logs/browser-fireside-initial.log).

[Read-only response probes](phase-5-metrics/two-tier-smoke-v3-20260903T1613+0800-2dc275c-r23/supplemental/storage-response-probes.json)
at `08:17:58Z` checked the same cache object through raw port 23102 and the
Portless storage alias. Both returned HTTP 200, `Content-Type: application/json`,
no `Content-Encoding`, and identical 12,444-byte bodies. The body begins
`1f8b08` and becomes valid JSON after gzip decompression; its SHA-256 is
`7378d7a5ef5b1fce85103e21be6ab1fb3ba80e556a92172b7b263de2b68cee3c`.
A metadata GET reported `contentEncoding: identity` for that gzip body.

This rules out an alias-only problem for this response. Static source inspection
supports a Fireside Storage encoding gap: Twodart's pinned watcher saves this
object with `gzip: true`, while `file_response` in
`crates/storage-front/src/lib.rs` does not emit the object's content encoding.
The metadata observation also requires investigating preservation of standard
upload metadata; adding a response header alone must not be assumed sufficient.
This is a diagnosis, not a completed fix or a new official-oracle capture.
